## ADDED Requirements

### Requirement: Маршруты журнала

HTTP API SHALL предоставлять создание, список, чтение, правку и удаление записей журнала:

- `POST /logs` создаёт запись и возвращает её со статусом 201
- `GET /logs` возвращает список со статусом 200
- `GET /logs/:id` возвращает запись со статусом 200
- `PATCH /logs/:id` возвращает изменённую запись со статусом 200
- `DELETE /logs/:id` возвращает статус 204

Неизвестный id на чтении, правке и удалении SHALL давать статус 404. Тело, которое нарушает правила журнала, SHALL давать статус 400, и журнал не меняется. Ответ с ошибкой SHALL быть JSON-объектом с полем `error`. Время в JSON SHALL быть строкой ISO-8601. Пустой конец SHALL быть `null`.

#### Scenario: Создание открытой записи

- **WHEN** клиент с действующим токеном отправляет `POST /logs` с наименованием и без конца
- **THEN** система отвечает 201 и телом записи с `end`, равным `null`

#### Scenario: Список за период

- **WHEN** клиент отправляет `GET /logs` с параметрами `from` и `to`
- **THEN** система отвечает 200 и списком записей, которые пересекают этот период

#### Scenario: Неизвестный id

- **WHEN** клиент отправляет `GET /logs/:id` с id, которого нет
- **THEN** система отвечает 404 и JSON с полем `error`

#### Scenario: Конец раньше начала

- **WHEN** клиент отправляет `POST /logs`, где конец раньше начала
- **THEN** система отвечает 400 и не создаёт запись

### Requirement: Правка отличает пропуск поля и пустой конец

На `PATCH /logs/:id` система SHALL менять только поля, присутствующие в теле. Поле `end` со значением `null` SHALL очищать конец. Отсутствие `end` в теле SHALL оставлять конец прежним.

#### Scenario: Закрытие

- **WHEN** клиент отправляет `PATCH /logs/:id` с моментом в `end`
- **THEN** система отвечает 200 и запись хранит этот конец

#### Scenario: Повторное открытие

- **WHEN** клиент отправляет `PATCH /logs/:id` с `end`, равным `null`
- **THEN** система отвечает 200 и конец записи пуст

#### Scenario: Конец не передан

- **WHEN** клиент отправляет `PATCH /logs/:id` только с новым наименованием
- **THEN** система меняет наименование и сохраняет прежний конец

### Requirement: Доступ по bearer-токену

Каждый маршрут `/logs` SHALL требовать заголовок `Authorization` со схемой `Bearer` и действующим токеном. Запрос без заголовка, с неизвестным токеном или с отозванным токеном SHALL получать статус 401 и не менять журнал.

#### Scenario: Без токена

- **WHEN** клиент отправляет `GET /logs` без заголовка `Authorization`
- **THEN** система отвечает 401

#### Scenario: Отозванный токен

- **WHEN** клиент отправляет `POST /logs` с отозванным токеном
- **THEN** система отвечает 401 и не создаёт запись

### Requirement: Документ OpenAPI

Система SHALL публиковать документ OpenAPI, сгенерированный из схем тех же маршрутов `/logs`. Документ SHALL описывать поля записи, пустой конец и схему безопасности bearer на операциях журнала. Чтение документа SHALL быть доступно без токена.

#### Scenario: Документ соответствует маршруту

- **WHEN** клиент запрашивает документ OpenAPI без токена
- **THEN** система отвечает телом документа, в котором есть `POST /logs` и схема bearer

### Requirement: Справочник Scalar

Система SHALL отдавать справочник Scalar по пути `/scalar` без токена. Справочник SHALL читать документ OpenAPI этого сервиса по пути `/scalar/openapi.json`.

#### Scenario: Открытие справочника

- **WHEN** клиент запрашивает `GET /scalar` без токена
- **THEN** система отвечает страницей справочника

#### Scenario: Документ для справочника

- **WHEN** клиент запрашивает `GET /scalar/openapi.json` без токена
- **THEN** система отвечает документом OpenAPI

### Requirement: Проверка живости

Система SHALL отвечать 200 на `GET /health` без токена после того, как начала слушать порт. Этот маршрут SHALL NOT возвращать записи журнала.

#### Scenario: Процесс принимает запросы

- **WHEN** клиент запрашивает `GET /health` без токена
- **THEN** система отвечает 200
